# ТЗ на рефакторинг Resource Picker

## Цель

`Resource Picker` нужен для подготовки PNG-ресурсов к использованию в `Group`, редактирования метаданных PNG для нарезки sprite sheet на кадры и контроля производного `resource_manifest.json`, с которым работает `ResourceManager`.

## Источники истины

1. Файлы `Group` являются единственным источником истины для содержимого manifest.
   - Переменные `GRAPHICS` в файлах `Group` определяют, какие PNG-ресурсы подключены к проекту.
   - Содержимое manifest нельзя редактировать вручную через UI.
   - Manifest должен строиться и обновляться только на основе файлов `Group`.

2. PNG-файл является единственным источником истины для метаданных нарезки.
   - `frame_width` и `frame_height` должны храниться в метаданных PNG.
   - `ResourceManager` должен использовать эти PNG-метаданные при нарезке sprite sheet на кадры.
   - Manifest может содержать производную копию этих данных только как индекс/кэш, но не как источник истины.

3. `resource_manifest.json` является производным индексом.
   - Он нужен `ResourceManager` для быстрой загрузки и проверки ресурсов.
   - Он строится из двух источников: `GRAPHICS` в `Group` и метаданных PNG.
   - Пользователь не должен править записи manifest напрямую.

## Основные сценарии

### 1. Получить PNG resource tuple

Пользователь открывает вкладку работы с PNG, выбирает нужный PNG в дереве `assets/` и нажимает кнопку `Get PNG resource`.

Инструмент копирует в буфер обмена tuple вида:

```python
("table", "main_screen.table")
```

Где:

- первый элемент - локальное имя слоя, полученное из имени PNG-файла;
- второй элемент - `resource_key`, построенный из пути PNG внутри `assets/`.

Пользователь самостоятельно вставляет этот tuple в переменную `GRAPHICS` нужного файла `Group`.

### 2. Посмотреть PNG

При выборе PNG должен отображаться предварительный просмотр изображения.

PNG рассматривается как sprite sheet, даже если фактически содержит один кадр.

### 3. Отредактировать PNG-метаданные

Пользователь вручную вводит параметры нарезки:

```text
frame_width
frame_height
```

Эти значения пользователь получает из внешнего графического приложения.

После сохранения значения должны быть записаны в метаданные самого PNG-файла.

Manifest при этом не должен редактироваться напрямую. Его можно обновить отдельной командой на вкладке manifest.

### 4. Построить manifest

Если manifest еще не создан, пользователь переходит на вкладку manifest и нажимает `Build Manifest`.

Команда должна:

1. Найти все файлы `Group`.
2. Прочитать переменные `GRAPHICS`.
3. Для каждого `resource_key` найти соответствующий PNG.
4. Прочитать из PNG метаданные `frame_width` и `frame_height`.
5. Построить `resource_manifest.json`.

### 5. Обновить manifest

Если manifest существует, но устарел, пользователь нажимает `Manifest Update`.

Команда должна синхронизировать состав manifest по актуальному источнику истины:

- `GRAPHICS` в файлах `Group`.

Manifest Update не должен требовать ручного редактирования записей manifest.

## Функциональные зоны интерфейса

### 1. PNG Explorer

Вкладка для работы с сырыми PNG-файлами из `assets/`.

Функции:

- рекурсивное дерево PNG-файлов;
- поиск по имени PNG-ресурса;
- выбор PNG;
- preview выбранного PNG;
- кнопка `Get PNG resource`;
- вывод и копирование tuple для `GRAPHICS`.

### 2. PNG Metadata Editor

Зона редактирования метаданных выбранного PNG.

Функции:

- показать текущие PNG-метаданные;
- редактировать `frame_width`;
- редактировать `frame_height`;
- сохранить значения в PNG-файл;
- показать предупреждение, если метаданные отсутствуют или некорректны.

### 3. Manifest Explorer

Вкладка для просмотра производного состояния manifest.

Структура дерева должна отражать подключение ресурсов к `Group`, а не просто структуру папки `assets/`.

Пример:

```text
table_group.py
└── ("table", "main_screen.table")

left_player_group.py
└── ("portrait_bg", "main_screen.p_portrait_bg")
```

Функции:

- просмотр дерева `Group -> PNG resources`;
- поиск по имени PNG-ресурса внутри manifest-дерева;
- кнопка `Build Manifest`;
- кнопка `Manifest Update`;
- отчет о добавленных, удаленных, отсутствующих и некорректных ресурсах.

### 4. Preview

Зона визуального просмотра выбранного PNG.

Функции:

- показывать выбранный PNG из `PNG Explorer`;
- показывать PNG, связанный с выбранной записью в `Manifest Explorer`;
- в будущем можно добавить отображение сетки нарезки по `frame_width` и `frame_height`.

### 5. Output / Warnings

Служебная зона для результата операций.

Функции:

- показывать скопированный tuple;
- показывать отчет `Build Manifest`;
- показывать отчет `Manifest Update`;
- показывать ошибки чтения PNG;
- показывать предупреждения по отсутствующим или некорректным PNG-метаданным.

## Поиск

Поиск должен быть контекстным.

Если активна вкладка `PNG Explorer`, поиск фильтрует дерево PNG-файлов из `assets/`.

Если активна вкладка `Manifest Explorer`, поиск фильтрует дерево manifest-представления `Group -> PNG resources`.

Поиск должен искать только по имени PNG-ресурса. Он не должен быть общим поиском по path, manifest JSON, статусам или служебному тексту.

## Что убрать из текущей модели

Нужно убрать или переосмыслить функции, которые создают ощущение ручного редактирования manifest:

- `Save record`;
- `Save + Copy GRAPHICS`;
- редактирование `resource_key` как manifest-записи;
- редактирование `path` как manifest-записи;
- ручное редактирование `frame_width` и `frame_height` внутри manifest.

Вместо этого:

- `Get PNG resource` копирует tuple для ручной вставки в `Group`;
- `Save PNG metadata` сохраняет размеры кадра в PNG;
- `Build Manifest` строит manifest из `Group` и PNG metadata;
- `Manifest Update` синхронизирует состав manifest по `GRAPHICS` в `Group`.

## Требования к ResourceManager

`ResourceManager` должен считать manifest производным индексом.

При построении manifest он должен:

- брать список ресурсов из `GRAPHICS` файлов `Group`;
- брать `frame_width` и `frame_height` из PNG metadata;
- проверять существование PNG-файлов;
- предупреждать об отсутствующих или некорректных метаданных;
- не считать старые значения manifest источником истины.

## Критерии готовности

Рефакторинг считается готовым, если:

1. Пользователь может выбрать PNG в `PNG Explorer` и получить tuple для `GRAPHICS`.
2. Пользователь может посмотреть preview выбранного PNG.
3. Пользователь может записать `frame_width` и `frame_height` в метаданные PNG.
4. Manifest нельзя редактировать вручную через форму записи.
5. `Build Manifest` строит manifest из `GRAPHICS` в `Group` и PNG metadata.
6. `Manifest Update` обновляет состав manifest по `GRAPHICS` в `Group`.
7. `Manifest Explorer` показывает дерево `Group -> PNG resources`.
8. Поиск работает контекстно по активной вкладке и ищет только имя PNG-ресурса.
9. Ошибки и предупреждения выводятся в отдельной зоне `Output / Warnings`.
